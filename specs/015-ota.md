# 015 — The machine updates itself (OTA)

> Status: **actually working.** `v0.1.0` was published and Ubuntu updated
> itself from build #127 to #129 by downloading from it, in 5.5 s. Windows
> was exercised and refused with the right reason, as designed. On the Mac
> **none of this has run yet**: the machine was offline the whole day.

## The problem

`deploy.sh` is the only path to the machines, and it runs **from here**.
While all three are on the same LAN that is just convenience. When the
MacBook travels, it stops being so: its build freezes on the last day
someone ran the deploy, and whoever finds out is the person far away,
without the Ubuntu machine nearby.

CI already publishes what is needed ([`013`](013-ci-cd.md)): on a `v*` tag,
a Release with the three packages and a `SHA256SUMS`. What was missing was
someone on the machines' side to consume it.

## The shape

One binary, `logi-ota`, on all three machines, woken by each system's
scheduler. It does, in order:

| # | Step | Why in this order |
|---|---|---|
| 1 | Asks `/healthz` for the current build | the file on disk may be new and the process old; only the live daemon does not lie |
| 2 | Reads `/releases/latest` from the API | |
| 3 | Picks the package by the system prefix | |
| 4 | Compares the name's `-<n>-<hash>` with what is running | `n` is `git rev-list --count`: it always grows, unlike the tag |
| 5 | Downloads `SHA256SUMS` and the package | |
| 6 | Checks the package's sha256 | without this OTA is just a downloader |
| 7 | Extracts and checks **each binary** against the internal `SHA256SUMS` | the package carries its own |
| 8 | Checks the commit stamp inside the daemon | the same question `construir-binarios.sh` asks before packaging |
| 9 | **Signs** (Mac only) | see below — it is the step that justifies everything |
| 10 | Checks library linkage and runs `logid --help` | **still in the staging folder**, with what works still in place |
| 11 | Copies the current binaries to `anterior/` | |
| 12 | Swaps | |
| 13 | Restarts the daemon | `systemctl --user restart` / `launchctl kickstart -k` |
| 14 | Checks `/healthz` for ~26 s | "I restarted" is not "it is serving" |
| 15 | If not confirmed: **rolls back** `anterior/`, restarts, checks again | |

The result of each run goes into `estado.json`, and the wizard's `ota` step
([`011`](011-onboarding.md)) shows it.

## The stone in the road, and why it goes away

The Windows and Mac packages come out of CI with `unsigned` in the name, and
that is not carelessness: the Authenticode key and the Mac keychain identity
do not leave the machines ([`008`](008-security.md)). Installing what CI
produces, raw, would undo exactly the work that took the most time in this
project:

- on the Mac, TCC ties **Screen Recording** to the binary's *designated
  requirement*. An ad-hoc binary is tied by cdhash, which changes on every
  build — the grant would die on every update, and only the machine's owner
  can restore it, by hand, in the interface;
- on Windows, an `.exe` without a valid signature is what Defender deleted
  at the moment of writing, twice, taking the scheduled task with it.

The way out is step 9: **the updater signs locally, before installing**. On
the Mac `assinar.sh` uses the stable identity from the `logi` keychain, so
the designated requirement does not change and **the permission survives**.
That is literally what the local identity exists for.

On Windows there is no equivalent way out, because the key is not there. So
there `logi-ota` **refuses to swap** and says why. It is no loss: that
machine does not travel, and what is gained is the panel knowing when it
fell behind. Swapping is still done by `deploy.sh`.

## The second stone: the Mac's ffmpeg

Step 10 (`conferir_ligacoes`) exists because the Mac is the only machine
that links against a brew library: its capture is `libavdevice`'s
`avfoundation` and its encoding is `h264_videotoolbox`
([`010`](010-remote-desktop.md)). Linux and Windows capture via
PipeWire/DXGI and encode via NVENC, which is loaded at runtime — no dylib.

And the **soname goes into the binary**. When the Mac package was opened
here, it asked for `libavcodec.63`; the MacBook has `libavcodec.61`. The
package was correct and **uninstallable**: step 10 would refuse the whole
update, naming the dylib, forever — and "forever" is the problem, because a
correct lock that stays engaged for weeks without anyone seeing protects
nothing.

The cause was the runner: `brew install ffmpeg` on a `macos-15` installs
9.0.2. The MacBook is on 7.1.

And the obvious fix did not work. `brew upgrade ffmpeg` on the MacBook **has
no bottle for Sonoma** (`arm64_sonoma` does not exist for 9.0.2, only
`sequoia` and `tahoe`): it would mean compiling ffmpeg from source on a
laptop, for hours, to be stuck on a major that changes by itself on the next
`brew upgrade`.

`ffmpeg@7` has a bottle for Sonoma **and** for the runner. So CI switched to
asking for the versioned formula:

| End | What it does |
|---|---|
| CI (`binarios.yml`) | `brew install ffmpeg@7`, `PKG_CONFIG_PATH=/opt/homebrew/opt/ffmpeg@7/lib/pkgconfig` |
| `construir-binarios.sh` | declares `FFMPEG_FORMULA` + `FFMPEG_SONAME` and **breaks the build** if any brew dylib comes from outside the prefix, or if the major is not the declared one |
| `deploy.sh` | checks, in the binary it installed, that the major is the declared one and that **every** requested dylib exists on the machine |
| Mac panel | `ffmpeg` line: do the dylibs the installed host asks for resolve here? Recipe: `brew install ffmpeg@7` |

### And the detail that took the premise apart

The idea was symmetric — `ffmpeg@7` on both ends, same prefix. On the
MacBook that **did not happen**, and `brew install ffmpeg@7` there was a
no-op:

```
/opt/homebrew/opt/ffmpeg@7 -> ../Cellar/ffmpeg/7.1_4   (alias, from Jan/2025)
brew list --versions          ->  ffmpeg 7.1_4   (no ffmpeg@7)
.../opt/ffmpeg@7/lib/pkgconfig/libavcodec.pc
                              ->  prefix=/opt/homebrew/Cellar/ffmpeg/7.1_4
```

That machine's brew treats `ffmpeg@7` as an **alias** of `ffmpeg` — after
all, its `ffmpeg` is still 7.x. On the runner, which has a current tap and
`ffmpeg` at 9.0.2, `ffmpeg@7` is a real keg-only.

Practical result: the CI binary asks for
`/opt/homebrew/opt/ffmpeg@7/lib/libavcodec.61.dylib`, and that path
**resolves on the Mac through the alias**, to the same keg. It is not theory
— it is the binary that OTA installed and that captured the screen.

Two consequences, and both are in the code:

- **What is load-bearing is the alias.** If one day that machine's
  unversioned `ffmpeg` moves to 9.x, the `@7` alias stops pointing to a 7
  keg and binaries coming from OTA stop loading. The failure is
  **visible**: the panel's `ffmpeg` line names the missing dylib, and the
  fix (`brew install ffmpeg@7`) then really installs a keg of its own.
- **The Mac's local build will never say `ffmpeg@7`**, because the `.pc`
  inside the alias points to the unversioned Cellar. That is why `deploy.sh`
  measures what needs to be true (declared major + every dylib resolves)
  and not the prefix. `construir-binarios.sh` stays strict on the prefix,
  because there the product is a **package** — and a package linked against
  the unversioned prefix does not install on a machine that only has the
  versioned keg.

### The cache trap that almost slipped through

Changing `PKG_CONFIG_PATH` does **not** make cargo relink. The `-L` comes
from the **cached** output of `ffmpeg-sys-next`'s build script; deleting
`target/release/logistream-host` does not help either, because cargo just
re-copies from `target/release/deps`. The first deploy after the pin
compiled in **0.09 s** and delivered the old binary saying `ok`.

Whoever switches formula needs:

```bash
cargo clean -p ffmpeg-sys-next -p logistream --release
```

The point of the check in `construir-binarios.sh` is the usual one in this
repo: a formula change on the runner becomes a **build failure**, not a
silent OTA refusal a week later.

## The orphan that would make OTA roll back a good update

Discovered while fixing something else, and it is the most serious flaw this
design has had.

The Mac's `logid` had **two owners**: the `ai.logi.logid` LaunchAgent and
the GUI, which started a child of its own when `/healthz` did not answer. At
boot the GUI won the race, the child became an orphan (`launchctl print`
said `state = spawn scheduled`, `last exit code = 1`) and the supervised
copy spent the day dying with `Address already in use`.

For OTA this is poison, and the sequence shows why:

```
step 12  installs the new binaries          ok
step 13  launchctl kickstart -k             kills the LAUNCHD copy
         ...                                the orphan keeps the port
step 14  /healthz                           the OLD build answers
step 15  roll back                           <-- rolls back what was right
```

In other words: the updater working perfectly would undo a correct update,
and record `revertido` in the state. The Ubuntu run passed because there was
no orphan there.

The fix comes in three layers, described in
[[../.claude/rules/one-supervisor-per-daemon]]: the GUI stopped being a
second supervisor; `Plano::limpar` (`pkill -x logid`) runs before the
restart, in OTA and in deploy; and the panel started comparing the stamp of
**whoever answers** with that of the **file on disk** — because the original
symptom was a deploy saying `ok` seven times over a machine that was serving
a ten-day-old binary.

## The clock belongs to the system, not the daemon

| Machine | Who wakes it | Interval |
|---|---|---|
| Ubuntu | `logi-ota.timer` (systemd user) | `OnBootSec=3min`, then 1 h |
| Mac | LaunchAgent `ai.logi.ota` | `StartInterval` 3600 |
| Windows | scheduled task `logi-ota` | `/sc hourly` |

Three reasons for it not to be a `logid` thread, and they add up:

1. **Whoever swaps the binary cannot die with it.** A thread inside `logid`
   would not survive the restart it requested itself, and there would be no
   one to check `/healthz` or to roll back.
2. **OTA needs to work with the daemon dead** — which is exactly the case
   where updating fixes things. A clock inside `logid` means a broken
   `logid` never fixes itself again.
3. The clock is already the supervisor's job on all three, and all three
   already have one.

`RunAtLoad false` on the Mac and `--conferir` on the wizard's first run for
the same practical reason: installing the clock must not apply an update
**in the middle of the HTTP request that installed it**, because that
restarts the `logid` that is answering. The price is that, after a boot, the
Mac may take up to an hour to look.

## The token, and what it changes in the trust model

The repo is private, so the API answers `200` with
`{"message":"Not Found"}` without authentication — an error that, if not
handled, would show up as "no package for mac" and send you looking in CI.
`logi-ota` distinguishes the two cases and names the missing file.

The token is a **fine-grained** PAT, `Contents: read`, **this repo only**,
at:

| Machine | Path |
|---|---|
| Ubuntu / Mac | `~/.config/logi/ota-token`, mode `600` |
| Windows | `%LOCALAPPDATA%\logid\ota-token` |

It never goes into `argv`: it reaches `curl` via `-K -`, on stdin. In
`argv` it would show up in any `ps` on the machine.

And here is the honest part: **this moves GitHub into the trust path.**
Until now GitHub received code that was already its own and returned an
artifact nobody installed. The "no cloud" rule ([`008`](008-security.md))
applied to the running system, and still applies to *data* — nothing from
the machines passes through there. But whoever controls the Release now
controls what runs on all three.

What actually mitigates this is **not** `SHA256SUMS`: it comes from the same
place as the package, and protects against a corrupted download, not against
a compromised origin. What mitigates it is step 9 — on the Mac, a binary only
gets the privileged permissions if it is signed **here**, with a key that is
not on GitHub. On Windows, nothing is installed. On Ubuntu, which is where
the key lives, OTA is a convenience, not a necessity.

## What was measured

### Against the real Release

`v0.1.0` went out with the four attachments (build #129 `92681b6`), and
Ubuntu was on #127:

```
$ logi-ota --conferir
novidade: ha o build #129 92681b6 publicado; aqui esta o #127

$ logi-ota
atualizado: atualizei para #129 92681b6 sozinho     # 5.5 s

$ curl -s localhost:8787/healthz
{"build":"92681b6","n":129,"ok":true}
```

Checked **from outside**, afterwards, by downloading the Release again: its
`SHA256SUMS` validates the package, and the five binaries installed in
`~/.local/bin` are byte for byte those of the package — `logid`,
`logistream-host`, `logistream-view`, `logistream-kvm` and `logi-ota`, all
`OK`.

On Windows, pointed at a fake Release with a higher `n`:

```
novidade: ha o build #999 abcdef1 publicado; aqui esta o #129 --
nao assino aqui: a chave do Authenticode vive no Ubuntu (specs/008);
rode o deploy
```

And it **downloaded nothing** — the package address was invalid on purpose,
and the refusal happens before the download.

### Against a local server

A `python3 -m http.server` serving a fake Release (`LOGI_OTA_API` exists for
this, and only for this):

| Case | Result |
|---|---|
| Build equal to the published one | `igual: em dia no build #123 37c4983`, nothing touched |
| `--forcar` with the real package | `atualizado`, 5 binaries swapped, `/healthz` confirmed, **3.3 s** |
| The 5 installed binaries | sha256 identical to the package's, checked afterwards |
| `/healthz` on a dead port | `revertido`, copied `anterior/` back, restarted, and said where the good copy was left |
| Without a valid token | `erro: o GitHub respondeu: Bad credentials` |

One of these runs proved something I had not planned to test: `--forcar`
swapped **`logi-ota` itself** for a version from the package that did not
have `LOGI_OTA_API`, and the next run went straight to the real API. The
updater updates itself, and on Unix that works because the swap is
`unlink` + new file — whatever is running keeps the old inode.

And the CI **Mac package** was opened and checked here, even with the
machine offline (`gh run download -n logi-mac`):

| Question | Answer |
|---|---|
| Layout that `apply.rs` expects | yes: folder `<name without .tar.gz>/` with the 4 binaries and the `SHA256SUMS` inside |
| `sha256sum -c SHA256SUMS` | 4 of 4 `OK` |
| Format | `Mach-O 64-bit arm64` on all four |
| Commit stamp in `logid` | present |
| Does `logi-ota` depend on brew? | **no, zero references** — that is what `construir-binarios.sh` now refuses, and what lets the updater start on a machine where the rest does not |
| `logistream-host` and `-view` depend on | `libavcodec.63`, `libavutil.61`, `libswscale.10`, `libavformat.63`, `libavdevice.63` — that is, the **runner's ffmpeg 9.x** |

That last row was the one that mattered, and it was **wrong on the CI
side**: the MacBook has major 7. It became the `ffmpeg@7` pin described
above. The all-or-nothing stays on purpose — installing only `logid` (which
does not depend on brew) would leave the control plane ahead of the screen
host, and an old binary on the other side of the bridge is the divergence
that gives no error, it just answers with yesterday's.

### On the Mac, on the machine, with the CI package

What was missing: step 9 (signing) and TCC survival. Measured with the
MacBook on the LAN, serving the **real CI package** (#133 `5a91d80`,
`gh run download -n logi-mac`) via `LOGI_OTA_API` — no fake Release
published, no token on disk:

```
$ ssh mac 'LOGI_OTA_API=http://192.168.1.44:8099 logi-ota'
atualizado: atualizei para #133 5a91d80 sozinho

$ ssh mac 'curl -s localhost:8787/healthz'
{"build":"5a91d80","n":133,"ok":true}
```

And the question the whole design exists to answer — the *designated
requirement*, before and after:

```
before designated => identifier "logistream-host" and certificate leaf = H"147f2d95...872242"
after  designated => identifier "logistream-host" and certificate leaf = H"147f2d95...872242"
```

Identical. TCC ties the grant to that predicate, so it remains valid. And it
did not stay theoretical: with the host LaunchAgent brought up **in the
graphical session** (`launchctl kickstart gui/501/ai.logi.logistream-host`,
because over SSH it does not come up — [[../.claude/rules/graphical-session]]),
the binary that came from CI captured:

```
  avfoundation: tela 1, 1920x1440, UYVY422
  h264_videotoolbox pronto, 11 Mbps alvo
  escutando em 0.0.0.0:9777
  acessibilidade concedida: teclado e mouse serao injetados
```

Two things learned there:

- the installed host's `otool -L` started pointing to
  `/opt/homebrew/opt/ffmpeg@7/...` — **OTA itself migrated** the binaries
  from the unversioned prefix to the versioned one;
- **the first avfoundation open after the swap took ~30 s**, and during that
  interval the log sits at `abrindo a tela 1...`, which is exactly the
  phrase that says "Screen Recording is missing". I waited 12 s on the first
  attempt and declared the permission dead. The following opens took
  **3 s** — that is, the cost is in the first contact with the new binary,
  not in the path. Thirty seconds before concluding anything.

And with the host up, the screen measured end to end by this machine's
`logistream-sink` against the Mac, on the LAN:

```
581 quadros inteiros em 10.0s = 58.1 fps
3249 datagramas, 2.8 Mbps
quadros perdidos (chegaram incompletos): 0
```

Zero loss. It is the host that CI compiled, signed locally, serving to
Ubuntu.

The SHA-256 is ours (`ota/src/sha256.rs`), and the 14 test vectors came from
coreutils' `sha256sum` and Python's `hashlib`, including the padding
boundaries (55/56/57, 63/64/65, 119/120/121) and a 3 MB blob. It is not a
crate because the check has to run the same on all three — and on Windows
the system equivalent would be `certutil -hashfile`, with its own output to
parse. Three tools and three parsers to compare 64 characters is more code
than the algorithm.

## Decisions

**System `curl` and `tar`, not crates.** Both exist on all three machines
and the repo already uses them ([`probe.rs`](../logid/src/probe.rs),
[`clip_files.rs`](../logid/src/clip_files.rs)). Bringing in `reqwest`/`rustls`
would mean a `ring` cross-compiled for mingw and a certificate chain of our
own, to end up with the same guarantee the system already gives.

**Compares `n`, not the tag.** A tag is picked by hand and comes out of
order. `n` is `git rev-list --count`.

**A `-sujo` ("dirty") stamp counts as the same commit.** Without that, a
freshly locally-deployed machine would download the same commit from the
Release for "different hash", in a loop.

**Never downgrades.** `#130` here and `#124` published is a newer local
deploy, not a problem to fix.

**Sign and test before swapping.** A binary that does not load is refused
with what works still in place. Swapping and then finding out is what forces
a rollback; checking first is what avoids needing one.

**Check linkage instead of executing**, for the graphical binaries:
`logistream-view` opens a window, and a window opening by itself in the
middle of someone's session is worse than the problem. On the Mac it is
`otool -L` with an existence test for each brew dylib — which is exactly the
known risk from [`013`](013-ci-cd.md); on Linux, `ldd | grep "not found"`.

**The port comes from the config.** Hardcoding 8787 would make OTA conclude
"daemon dead" on a machine that only changed port — and a dead daemon is the
case where it installs without checking anything. The scan stops at the
first table, because each `[[hosts]]` has a `port = 22` that belongs to SSH.

## Known limits

- ~~**The Mac was not tested.**~~ Tested: `#132 -> #133` with the CI
  package, local signing, identical DR and capture working afterwards
  (above). What was **not** exercised there is the GitHub API path — the
  token is missing — nor the rollback, which was proven on Ubuntu.
- **The ffmpeg major is still a coupling**, now declared: both ends ask for
  `ffmpeg@7` and the build breaks if they diverge (above). What this does
  **not** solve: whoever installs another major by hand on the Mac takes
  down OTA there until it is uninstalled. The panel shows it as pending, and
  step 10's refusal names the dylib.
- **`gui/main.js` does not travel in the package.** CI does not package the
  Electron shell ([`013`](013-ci-cd.md)), so the window and the tray stay at
  the version of the last deploy. The *page* follows the binary (it goes via
  `include_str!`), which covers most of it. On the Mac this was worse until
  today: the shell lived inside an `app.asar` that no step touched — now it
  is a loose `Resources/app/` and travels via rsync like the Windows one.
- **Nothing protects a screen session in progress.** Swapping the file does
  not interrupt whatever is running (old inode), and restarting `logid` does
  not take down the screen host — but that is a consequence of the design,
  not an explicit lock.
- **The Mac's clock only counts with the machine awake and logged in.** A
  LaunchAgent does not run at the login screen or while sleeping. For a
  laptop that is the right behavior; for the other two, it is luck that they
  are desktops.
- **A run that fails at step 15 leaves the machine with the old build and a
  full `anterior/`.** The message gives the path, but there is no alarm at
  all beyond the panel.
- **The tag has to be pushed by hand.** Nothing here creates a Release. The
  recipe is in [`013`](013-ci-cd.md#publishing-a-version) — and since the
  release job waits for all three packages, a missing macOS runner (it has
  happened) delays the Release the other two machines were going to consume.
