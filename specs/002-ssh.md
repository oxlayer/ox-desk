# 002 — SSH and bootstrap

## Current state (working)

```
Host windows-host
    HostName windows-host.local
    IdentityFile ~/.ssh/id_ed25519_windows
    IdentitiesOnly yes
    AddKeysToAgent yes
    User user
```

A dedicated ed25519 key, **with a passphrase**, held for the session by
GNOME's `gcr-ssh-agent` (`SSH_AUTH_SOCK=/run/user/1000/gcr/ssh`): it asks
once per login and then serves automation without ever exposing the
phrase.

On Windows, `windows-ssh.ps1` installs OpenSSH Server, opens port 22 on
the Private profile and sets PowerShell as the shell.

## The two traps already paid for

**`administrators_authorized_keys`.** For an account in the
Administrators group, the Windows sshd **ignores**
`~/.ssh/authorized_keys`. It reads
`C:\ProgramData\ssh\administrators_authorized_keys` and **silently
discards** it if the ACL is not restricted — hence the
`icacls /inheritance:r` with permission only for Administrators and SYSTEM.

**`known_hosts` tied to an IP.** Switching from IP to name made
everything fail with `Host key verification failed`. The right fix is not
a blind `accept-new`: it is copying the *same* already-trusted key to the
new name and checking the fingerprint. Recipe in the README.

## What is missing: `POST /api/bootstrap/{id}`

Provision the other machine without copying a `.ps1` by hand. An
idempotent sequence, each step checking before acting:

1. **Reachability** — resolve `windows-host.local`, test port 22.
2. **Identity** — ensure the key; if missing, generate and install it
   (asking the user for the passphrase, never choosing one).
3. **Capabilities** — detect `winget`, Windows version, whether it is Pro.
4. **Packages** — Deskflow and KDE Connect via `winget install`, with
   `--accept-*-agreements`. Already validated today: KDE Connect went in
   this way, hash verified.
5. **Firewall** — the rules **the installers do not create**. KDE
   Connect was listening on 1716 and no `*KDE*` rule existed; Deskflow
   likewise on 24800. This step is not optional, it is the #1 cause of
   "I installed it and it doesn't work".
6. **Autostart** — shortcut in `shell:startup` (logon, not a service: the
   server needs a user session to capture input).
7. **Verify** — report what changed and what was already right.

## Structural limit: session isolation

A command over SSH on Windows **does not reach the interactive session**.
Verified twice today:

- Launching `kdeconnect-indicator.exe` over SSH opens nothing on the
  desktop; trying via `schtasks /it` did not come up either.
- `Set-Clipboard` over SSH writes to a clipboard that the user session's
  `kdeconnectd` does not see — `Get-Clipboard` in the same SSH session
  returns the value, which makes the test deceptively "green".

**Design consequence:** the bootstrap handles installation, firewall,
registry and files. Anything that needs the graphical session has to run
**in the agent**, inside that session — that is half the reason a
`logid-agent` exists on Windows instead of just SSH.

## The daemon's `ssh` could not resolve the name, and the terminal's could (2026-11-03)

This cost several rounds and would have hurt silently, so it is written down.

Symptom: with `sshd` enabled on Ubuntu and the key authorized, the
**Windows** `focus::plan` blocked with

```
dead-man's switch no alvo
  agente nao respondeu (ssh: Could not resolve hostname ubuntu-host: ...)
```

while `ssh ubuntu hostname` from the terminal worked, exit 0, 0.1 s.

### What was measured, in the same scheduled-task context

| test | result |
|---|---|
| `ping ubuntu-host.local` | resolves (IPv6, 1 ms) |
| `[System.Net.Dns]::GetHostAddresses('ubuntu-host.local')` | resolves (v6 **and** v4) |
| same with the short name `ubuntu-host` | resolves |
| `ssh` by name, launched by `cmd.exe` **from the task** | works, exit 0 |
| `ssh` by name, launched **by the daemon** | `Could not resolve hostname` |
| `ssh` by IP, launched by the daemon | works |

The OS resolver sees the name in every case. What does not see it is
`ssh`, and **only** when the parent is the daemon. Swapping `.local` for
the short name did not fix it — it is not the name format.

### The way out: resolve where it works

[`probe::ssh_addr_opts`](../logid/src/probe.rs) resolves in-process — the
daemon was already doing this successfully, it is how the TCP probe marks
`ubuntu-host online=true` — and hands over the ready address:

```
-o HostName=<ip resolved right now>  -o HostKeyAlias=<name from config>
```

It does not break the rule of never writing an IP ([`007`](007-device-routing.md)):
the config still holds only names, resolution happens **on every call**,
and an IP change is absorbed on its own. `HostKeyAlias` keeps the key's
identity tied to the name — without it, each new IP would look like an
unknown host and `StrictHostKeyChecking` would block it.

It applies to `ssh` and to `sftp` (the file browser had the same hole).

> Same family as mDNS on Linux, where `getaddrinfo` with `AF_UNSPEC`
> gives up on `.local` because of `[NOTFOUND=return]` in nsswitch and only
> `getent` resolves. Two OSes, two different reasons, one pattern: **do not
> delegate name resolution to a child process when you can already
> resolve it yourself.**

### Nested ssh needs `-n`

Twice I thought `ssh` had hung when what had hung was my harness: calling
`ssh` **from inside** an SSH session without `-n` leaves it reading a
stdin that never closes.

The daemon does not have this problem by construction —
`Command::output()` already hands the child a closed stdin — but any
manual test over nested SSH needs `-n`.
